# Design the work, then the prompt

Last verified: 2026-09-28

Academy's prompting text supplies the practical starting points: purpose, useful context, desired result and iteration. This pack applies them as a compact contract: deliverable, audience, inputs, non-negotiable constraints, uncertainty policy and observable checks. Inspect available files first; ask only questions that change a consequential decision. Mark reversible defaults as proposals, not user requirements.

For a capable reasoning model, begin with the goal and acceptance conditions. Avoid mandatory essays about every reasoning step or a rigid sequence that does not serve the task. If a failure is observed, add the smallest relevant guidance: an output schema for parsing errors, evidence boundaries for invented facts, varied examples for ambiguous categories, or a must-preserve clause for lost negation. Without failing outputs, label the diagnosis provisional.

The Astra developer article warns that overly broad Skill descriptions and accumulated instructions can consume context or overconstrain work. Keep discovery descriptions narrow and supporting instructions on demand. For capable models prefer outcome constraints; for a bounded weaker-worker stage, provide the exact input/output contract and the small examples it needs. Do not remove privacy or irreversible-action boundaries in the name of autonomy.

Version the original and revised prompts. Test on representative inputs rather than judging their appearance. Return the usable prompt or artifact first. If asked to perform the work, do not substitute a prompt for another AI unless delegation is actually part of the request.
